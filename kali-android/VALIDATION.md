# Verification record

## Verified

- The final `com.kp.kali` development APK is signed and builds with Android SDK33/AGP7.4.2/Gradle7.6.4/JDK17. Minimum and target Android API are29; packaged ABIs are arm64-v8a and x86_64.
- All25 project-owned JUnit tests passed: 13 disk import/resource/recovery tests, ten VM session/lifecycle-state tests and two bounded/retained log tests. No tests skipped.
- Android lint completed without errors. Warnings remain for the intentionally old Play Store target, old upstream-compatible dependency versions, synchronous pre-launch preference persistence, basic free-space estimation and untranslated development UI strings. Only `ExpiredTargetSdkVersion` is explicitly downgraded to a visible warning because this APK is for sideloaded development, not Play submission.
- The18 packaged native libraries match the official Limbo6.0.1 release APK byte-for-byte. SHA256 is pinned in `toolchain-lock.json`; all10 accompanying native-source archive hashes were checked.
- A clean bootstrap and its repeat succeeded in a separate temporary build-prerequisite directory. Neither test required disabling TLS or artifact checks.
- Earlier Android API29 x86_64 software-emulator testing displayed the actual setup screen, loaded the real native QEMU engine and booted the512-byte BIOS fixture in `tests/android/boot-proof.S`. The guest screen read **“QEMU guest boot verified - NOT Kali”**. This is evidence of native guest execution, not a Kali OS test.
- An independent code reviewer identified three Important issues (abandoned import staging files, unavailable native-failure diagnostics, and controls re-enabling during process teardown). Four regression tests first failed, then passed with the fixes. Startup now recovers abandoned staging files; current/previous diagnostic logs are bounded and readable; `EXITING` prevents restart/import while the engine process unloads.
- Subsequent Android testing exposed a native engine that would not exit while its display was suspended. Version0.1.1 adds a confirmed-only, own-process termination watchdog; the new deadline regression first failed, then the25-test suite passed. Unconfirmed Force stop and ordinary graceful-shutdown timeout cannot kill the process.
- A fresh accessibility snapshot failed while unchanged status text was being rewritten once per second. Rendering now updates text only when its value changes; fresh snapshots then succeeded. The test runner also refuses to reuse stale UI XML.

## Android integration results — version0.1.1

The signed versionCode2 APK ran on the dedicated API29 x86_64 software emulator. The actual guest screen displayed SeaBIOS and **“QEMU guest boot verified - NOT Kali”**. Checks passed for the launcher reporting native QMP RUNNING, disabled duplicate Start, returning from the desktop, actual activity recreation, guest-shutdown timeout, confirmed force stop, reopening with the disk retained, and recovery of an orphaned import without deleting the valid disk.

The native-failure scenario was resumed after correcting its test fixture: QEMU accepted a sparse QCOW2 with missing table contents, so that input did not prove a fatal startup error. An explicitly unsupported reference-count width (`refcount_order=100`) then caused the expected native rejection, and the actual app displayed that error in Startup diagnostics after reopening. The negative scenario and the final guest relaunch completed successfully. This was a main integration run plus a resumed negative-image check, not one uninterrupted green run.

Evidence is recorded in `.tools/android-smoke-release.log` and `.tools/android-smoke/`, including `result.txt`, screenshots and the captured diagnostic view. The test runner is destructive to the dedicated `kali-test` app disk and must never be aimed at a user's phone. Earlier attempts also exposed and corrected test-harness issues with Android dialog capitalization, UI-transition timing and stale hierarchy snapshots; those failed attempts were not counted as passes.

## Historical0.1.1 limitations (superseded by current validation above)

- A real Kali OS boot, desktop applications, guest `sudo`, tool compatibility or guest networking.
- A physical ARM64 Android phone or a16KiB-page Android device.
- A large real Kali disk import through Android document providers; stream/replacement/recovery behavior was covered by core file tests and Android orphan recovery.
- Rebuilding native QEMU/dependency libraries from source or reproducing the upstream binary byte-for-byte from those sources.
- A full legal/license audit, a security hardening audit, or Play Store release compliance.

Version0.1.1 required a manually imported BIOS disk. Current versions bundle the boot kernel/initramfs and automatically download the pinned desktop layers. Guest root never supplies Android root or direct phone Wi-Fi hardware capabilities.
